Dependencias e Ordem de Implementacao

Toda feature em uma API em camadas segue uma ordem natural de dependencias. Cada camada depende apenas da camada imediatamente abaixo. Seguir essa ordem evita erros de compilacao e facilita o entendimento do codigo.

1. Model
models/Example.kt
Define a estrutura de dados. Tudo depende dele.
↓
2. Constants + MongoConfig
utils/Constants.kt & config/MongoConfig.kt
Registra o nome da colecao e a conexao tipada.
↓
3. Seed
DatabaseSeed.kt
Popula o banco com dados de exemplo para testes manuais.
↓
4. Repository Interface
repositories/ExampleRepository.kt
Define o contrato — o que o repositorio deve fazer.
↓
5. Repository Impl
repositories/ExampleRepositoryImpl.kt
Implementa o contrato usando KMongo.
↓
6. DTOs de Requisicao
dtos/request/ExampleRequests.kt
Moldes para os dados recebidos via HTTP.
↓
7. Service
services/ExampleService.kt
Regras de negocio. Depende do Repository (interface).
↓
8. Routes
routes/ExampleRoutes.kt
Endpoints HTTP. Depende do Service.
↓
9. Koin + Application
config/KoinModules.kt & Application.kt
Registra as dependencias e as rotas no servidor.
Por que essa ordem importa? O compilador Kotlin precisa conhecer os tipos antes de usá-los. Se você tentar criar o ExampleService antes de ter ExampleRepository, terá erros de "Unresolved reference". Seguir a ordem das dependencias evita esse problema.

1 Model — Example.kt

O Model e a representacao de um objeto de negocio no sistema. No Kotlin, usamos data class para modelos de dados, pois ela gera automaticamente equals(), hashCode(), toString() e copy().

1.1 A data class Example

@Serializable
data class Example(
    val id: String? = null,           // null antes de ser salvo no banco
    val nome: String,
    val email: String,
    val enumExample: Set<EnumExample>,  // conjunto — sem duplicatas
    val ativo: Boolean = true,
    @Contextual val createdAt: Instant = Instant.now(),
    @Contextual val updatedAt: Instant? = null
)

1.2 O enum class EnumExample

Um enum class define um conjunto fechado e seguro de valores possiveis. Isso e muito melhor do que usar String, pois o compilador garante que valores invalidos sejam detectados em tempo de compilacao. 

enum class EnumExample {
    EXAMPLE_ONE,
    EXAMPLE_TWO,
    EXAMPLE_THREE,
    EXAMPLE_FOUR
}
models/Example.kt
Por que usar Set<EnumExample> e nao List<String>?
  • Set garante que nao haja valores duplicados (ex: [EXAMPLE_ONE, EXAMPLE_ONE] vira [EXAMPLE_ONE]).
  • EnumExample garante que apenas valores validos sejam aceitos — o compilador rejeita qualquer outro valor.
  • Com List<String>, um erro de digitacao como "EXAMPLE_ONEE" so seria detectado em runtime.

1.3 Anotacoes de serializacao

Duas anotacoes sao essenciais para que o Ktor consiga serializar/deserializar o modelo:

AnotacaoOnde usarPara que serve
@Serializable Na data class Habilita a serializacao automatica pelo plugin do Kotlin. Sem ela, o Ktor lanca SerializationException.
@Contextual Nos campos Instant java.time.Instant nao tem um serializador padrao no kotlinx. @Contextual delega para o serializador registrado em AppJson.

2 Constants — Registrando o nome da colecao

Nunca use strings literais espalhadas pelo codigo para nomear colecoes MongoDB. Se o nome da colecao mudar, voce precisaria alterar em varios lugares. O padrao correto e centralizar em Constants. 

object Constants {
    // ... outras constantes ...

    // Colecoes MongoDB
    const val COLLECTION_USUARIOS = "usuarios"
    const val COLLECTION_EXAMPLES = "examples"  // <-- adicionado
}
utils/Constants.kt
Vantagem: refatoracao segura Se a colecao se chamar "exemplo" no futuro, voce altera apenas Constants.COLLECTION_EXAMPLES — o compilador encontra todos os usos automaticamente.

3 MongoConfig — Colecao tipada

O MongoConfig e a classe que gerencia a conexao com o MongoDB. Para cada colecao, adicionamos uma propriedade que retorna uma MongoCollection tipada com o nosso Model. 

class MongoConfig(
    connectionString: String = System.getenv("MONGO_URI") ?: "...",
    databaseName:     String = System.getenv("MONGO_DB") ?: "Aula"
) {
    private val client = KMongo.createClient(connectionString)
    val database: MongoDatabase = client.getDatabase(databaseName)

    val usuarios get() = database.getCollection<Usuario>(Constants.COLLECTION_USUARIOS)
    val examples get() = database.getCollection<Example>(Constants.COLLECTION_EXAMPLES)  // <-- adicionado
}
config/MongoConfig.kt
getCollection<Example>() O KMongo usa o tipo generico <Example> para serializar e deserializar automaticamente os documentos BSON para objetos Kotlin. Sem o tipo, voces receberiam um Document generico e teriam que fazer o mapeamento manual.

4 Seed — DatabaseSeed.kt

O Seed e um script executado separadamente (./gradlew seed) que popula o banco de dados com dados de exemplo. Ele usa o driver MongoDB Java puro (sem KMongo) para evitar dependencias circulares, e o Kotlin-Faker para gerar dados ficticios de forma automatica e realista.

4.2 Registros gerados com Kotlin-Faker (recursivo)

O Kotlin-Faker gera dados ficticios mas realistas: nomes, emails, nomes de empresas. O loop abaixo cria FAKE_EXAMPLES_COUNT registros de forma recursiva usando .map { }, que e a forma funcional de um loop que produz uma lista. 

val faker = Faker()
val enumExamples = listOf("EXAMPLE_ONE", "EXAMPLE_TWO", "EXAMPLE_THREE", "EXAMPLE_FOUR")

val fakeExamples = (1..FAKE_EXAMPLES_COUNT).map { i ->
    val nome        = faker.company.name()    // ex: "Acme Corp"
    val email       = faker.internet.email()  // ex: "john@example.com"

    // Seleciona de 1 a 3 enums aleatorios da lista
    val selectedEnums = enumExamples
        .shuffled()                            // embaralha a lista
        .take(faker.random.nextInt(1, enumExamples.size)) // pega 1, 2 ou 3

    Document(mapOf(
        "_id"         to "example-$i-" + UUID.randomUUID().toString().take(8),
        "nome"        to nome,
        "email"       to email,
        "enumExample" to selectedEnums,
        "ativo"       to faker.random.nextBoolean(),
        "createdAt"   to now
    ))
}

examples.insertMany(fakeExamples)
println("  ${examples.countDocuments()} examples inseridos.")
DatabaseSeed.kt
Por que usar .map em vez de for? O .map { } e funcional: ele transforma cada elemento de uma sequencia em outro, retornando uma nova lista sem efeitos colaterais. O resultado e imutavel e mais facil de raciocinar. O for seria imperativo e exigiria uma lista mutavel (mutableListOf()) para acumular resultados.

5 Repository Interface

A interface define um contrato: quais operacoes o repositorio deve ser capaz de executar, sem dizer como. Isso e o principio da Inversao de Dependencias (o "D" do SOLID): o Service depende de uma abstracao, nao de uma implementacao concreta.

5.1 O contrato completo

/**
 * Interface do repositório de Examples.
 * Contrato para operações CRUD e consultas específicas.
 */
interface ExampleRepository {
    fun findById(id: String): Example?
    fun findByEmail(email: String): Example?
    fun findAll(page: Int, limit: Int, filters: Map<String, Any?> = emptyMap()): Pair<List<Example>, Long>
    fun findByEnum(enumValue: EnumExample, page: Int, limit: Int): Pair<List<Example>, Long>
    fun insert(example: Example): Example
    fun update(id: String, updates: Map<String, Any?>): Boolean
    fun delete(id: String): Boolean
}
repositories/ExampleRepository.kt

5.2 Por que findByEnum existe na interface?

O metodo findByEnum e uma consulta especializada que vai alem do CRUD basico. Ela reflete um requisito de negocio: "preciso listar todos os examples que contem um determinado valor de enum". Incluir isso na interface garante que qualquer implementacao (KMongo, em memoria para testes, etc.) precise suportar essa consulta.

Pair<List<Example>, Long> O retorno em Pair e uma convencao do projeto para paginacao: o primeiro elemento e a lista de documentos da pagina atual, e o segundo e o total de documentos que existem no banco (necessario para calcular o numero total de paginas).

6.1 findAll com filtros dinamicos

override fun findAll(page: Int, limit: Int, filters: Map<String, Any?>): Pair<List<Example>, Long> {
    val bsonFilters = buildFilters(filters)          // converte Map para filtros BSON
    val total = collection.countDocuments(and(bsonFilters))
    val docs  = collection.find(and(bsonFilters))
        .skip((page - 1) * limit)                    // offset da pagina
        .limit(limit)
        .toList()
    return Pair(docs, total)
}
repositories/ExampleRepositoryImpl.kt

6.2 findByEnum — consulta em campo Set

Para buscar documentos onde um Set contem um valor especifico, o KMongo usa o operador contains, que gera um filtro MongoDB $elemMatch. 

override fun findByEnum(enumValue: EnumExample, page: Int, limit: Int): Pair<List<Example>, Long> {
    // "contains" verifica se o Set enumExample contem o valor
    val filter = Example::enumExample contains enumValue
    val total  = collection.countDocuments(filter)
    val docs   = collection.find(filter)
        .skip((page - 1) * limit)
        .limit(limit)
        .toList()
    return Pair(docs, total)
}
repositories/ExampleRepositoryImpl.kt

6.3 buildFilters — filtragem dinamica

O metodo buildFilters converte um Map<String, Any?> em uma lista de filtros BSON. Valores null sao ignorados, o que permite que o cliente envie apenas os filtros que deseja aplicar. 

private fun buildFilters(filters: Map<String, Any?>): List<Bson> {
    return filters.mapNotNull { (key, value) ->
        when {
            value == null         -> null             // ignora filtros nulos
            key == "nome"        -> Example::nome regex Regex(".*$value.*", RegexOption.IGNORE_CASE)
            key == "email"       -> Example::email regex Regex(".*$value.*", RegexOption.IGNORE_CASE)
            key == "ativo"       -> Example::ativo eq (value as Boolean)
            key == "enumExample" -> Example::enumExample contains EnumExample.valueOf(value as String)
            else                  -> null
        }
    }
}
repositories/ExampleRepositoryImpl.kt
mapNotNull Equivalente a .map { }.filter { it != null } em uma unica operacao. Cada entrada do Map de filtros e avaliada: se o resultado for null (filtro nao reconhecido ou valor ausente), ele e descartado da lista final.

7 DTOs de Requisicao

DTOs (Data Transfer Objects) sao classes que representam o formato dos dados que chegam via HTTP. Eles nunca sao iguais ao Model — o Model pode ter campos como senhaHash, createdAt ou id que nao devem ser expostos nem recebidos diretamente. 

import kotlinx.serialization.Serializable

// DTO para criacao de um novo Example
@Serializable
data class CreateExampleRequest(
    val nome:        String,
    val email:       String,
    val enumExample: List<String>   // recebe como String, valida no Service
)

// DTO para atualizacao parcial — todos os campos opcionais
@Serializable
data class UpdateExampleRequest(
    val nome:        String?       = null,
    val email:       String?       = null,
    val enumExample: List<String>? = null,
    val ativo:       Boolean?      = null
)
dtos/request/ExampleRequests.kt
Por que enumExample e List<String> no DTO e nao Set<EnumExample>?
  • O JSON que chega pelo HTTP e texto: ["EXAMPLE_ONE", "EXAMPLE_TWO"]
  • Receber como List<String> e mais resiliente — se vier um valor invalido, o Service lanca um erro amigavel (ApiException 400)
  • Se recebessemos direto como EnumExample, um valor invalido causaria um erro de deserializacao generico, difcil de tratar

8.1 Regra: Email unico

REGRA Nao pode existir dois Examples com o mesmo e-mail. 

fun criar(request: CreateExampleRequest): Example {
    // Consulta o repositorio para checar se o email ja existe
    if (exampleRepository.findByEmail(request.email) != null)
        throw ApiException(400, "E-mail já cadastrado para outro example")

    val enums = parseEnums(request.enumExample)

    val example = Example(
        id          = UUID.randomUUID().toString(),  // Service gera o ID
        nome        = request.nome.trim(),
        email       = request.email.lowercase().trim(),  // normaliza para minusculo
        enumExample = enums,
        ativo       = true,
        createdAt   = Instant.now()
    )

    return exampleRepository.insert(example)
}
services/ExampleService.kt
Por que o Service gera o ID e nao o Repository? O Service tem controle total sobre a criacao da entidade — incluindo o ID. Isso permite que o Service use o ID antes mesmo do insert (por exemplo, para criar relacoes entre entidades). O Repository apenas persiste o que o Service entrega.

8.2 Regra: Validacao de enums

REGRA Todos os valores do campo enumExample devem ser validos. Ao menos um deve ser informado. 

private fun parseEnum(value: String): EnumExample {
    return try {
        EnumExample.valueOf(value.uppercase())
    } catch (_: Exception) {
        // Mensagem de erro com os valores validos listados automaticamente
        throw ApiException(400, "Enum inválido: $value. Valores aceitos: ${EnumExample.entries.joinToString()}")
    }
}

private fun parseEnums(values: List<String>): Set<EnumExample> {
    if (values.isEmpty())
        throw ApiException(400, "Ao menos um enumExample deve ser informado")
    return values.map { parseEnum(it) }.toSet()   // converte para Set (sem duplicatas)
}
services/ExampleService.kt

8.3 Regra: Ativar e Desativar separadamente

REGRA Ativar e desativar sao operacoes distintas — nao se alterna com PATCH no campo ativo. Isso e uma boa pratica: deixa a intencao explicita e permite logar/auditar cada acao separadamente. 

fun ativar(id: String): Example {
    buscarPorId(id)  // verifica existencia — lanca 404 se nao encontrar
    exampleRepository.update(id, mapOf(
        "ativo"     to true,
        "updatedAt" to Instant.now()
    ))
    return buscarPorId(id)   // retorna o estado atual do banco
}

fun desativar(id: String): Example {
    buscarPorId(id)
    exampleRepository.update(id, mapOf(
        "ativo"     to false,
        "updatedAt" to Instant.now()
    ))
    return buscarPorId(id)
}
services/ExampleService.kt

8.4 Regra: Nao deletar example ativo

REGRA Um Example so pode ser deletado se estiver inativo (ativo = false). Isso protege contra remocoes acidentais de dados em uso. 

fun deletar(id: String) {
    val example = buscarPorId(id)   // lanca 404 se nao existir

    // Guarda de negocio: so deleta se estiver inativo
    if (example.ativo)
        throw ApiException(400, "Desative o example antes de deletá-lo")

    exampleRepository.delete(id)
}
services/ExampleService.kt
Padrao: verificar existencia primeiro Todo metodo que opera sobre um ID comeca com buscarPorId(id). Isso garante que a resposta seja sempre 404 Not Found quando o ID nao existe, em vez de um erro generico ou silencioso.

9.2 Codigo completo

fun Route.exampleRoutes() {
    val exampleService by inject<ExampleService>()

    authenticate("auth-jwt") {
        route("/examples") {

            // GET /examples
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO) {
                get {
                    val pagination = call.parsePagination()
                    val filters = mapOf(
                        "nome"        to call.request.queryParameters["nome"],
                        "email"       to call.request.queryParameters["email"],
                        "ativo"       to call.request.queryParameters["ativo"]?.toBooleanStrictOrNull(),
                        "enumExample" to call.request.queryParameters["enumExample"]
                    )
                    call.respondSuccess(exampleService.listar(pagination, filters))
                }
            }

            // GET /examples/enum/{enumValue}
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO, Papel.OPERADOR) {
                get("/enum/{enumValue}") {
                    val enumValue  = call.parameters["enumValue"]!!
                    val pagination = call.parsePagination()
                    call.respondSuccess(exampleService.buscarPorEnum(enumValue, pagination))
                }
            }

            // GET /examples/{id}
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO, Papel.OPERADOR) {
                get("/{id}") {
                    val id = call.parameters["id"]!!
                    call.respondSuccess(exampleService.buscarPorId(id))
                }
            }

            // POST /examples
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO) {
                post {
                    val request = call.receive<CreateExampleRequest>()
                    val criado  = exampleService.criar(request)
                    call.respondSuccess(criado, "Example criado com sucesso", HttpStatusCode.Created)
                }
            }

            // PATCH /examples/{id}
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO) {
                patch("/{id}") {
                    val id      = call.parameters["id"]!!
                    val request = call.receive<UpdateExampleRequest>()
                    call.respondSuccess(exampleService.atualizar(id, request), "Example atualizado")
                }
            }

            // PATCH /examples/{id}/ativar
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO) {
                patch("/{id}/ativar") {
                    val id = call.parameters["id"]!!
                    call.respondSuccess(exampleService.ativar(id), "Example ativado")
                }
            }

            // PATCH /examples/{id}/desativar
            authorize(Papel.ADMIN_PLATAFORMA, Papel.ADMIN_INSTITUICAO) {
                patch("/{id}/desativar") {
                    val id = call.parameters["id"]!!
                    call.respondSuccess(exampleService.desativar(id), "Example desativado")
                }
            }

            // DELETE /examples/{id}
            authorize(Papel.ADMIN_PLATAFORMA) {
                delete("/{id}") {
                    val id = call.parameters["id"]!!
                    exampleService.deletar(id)
                    call.respondEmptySuccess("Example removido")
                }
            }
        }
    }
}

10 Injecao de Dependencia e Registro

10.1 KoinModules.kt

Para que o Koin possa injetar o ExampleService na Route e o ExampleRepository no Service, precisamos registra-los no modulo do Koin. Cada single { } cria uma instancia singleton — um unico objeto compartilhado por toda a aplicacao. 

val appModule = module {

    // Config
    single { MongoConfig() }
    single { JwtConfig() }

    // Repositories — <Interface> { Implementacao(dependencias) }
    single<UsuarioRepository> { UsuarioRepositoryImpl(get<MongoConfig>().usuarios) }
    single<ExampleRepository>  { ExampleRepositoryImpl(get<MongoConfig>().examples) }  // <-- novo

    // Services
    single { AuthService(get(), get(), get()) }
    single { UsuarioService(get(), get()) }
    single { PerfilService(get()) }
    single { ExampleService(get()) }    // get() injeta ExampleRepository automaticamente
}
config/KoinModules.kt
Como o Koin resolve o get() automaticamente? Quando o Koin ve ExampleService(get()), ele procura em seu registro interno alguma definicao cujo tipo bate com o primeiro parametro do construtor de ExampleService, que e ExampleRepository. Ele encontra single<ExampleRepository> { ExampleRepositoryImpl(...) } e injeta a implementacao. O Service nem sabe que e uma ExampleRepositoryImpl.

10.2 Application.kt

Por fim, a rota e registrada no servidor adicionando exampleRoutes() dentro do bloco routing { }: 

fun Application.module() {
    install(Koin) { modules(appModule) }
    val jwtConfig = JwtConfig()

    configureContentNegotiation()
    configureCORS()
    configureAuthentication(jwtConfig)
    configureStatusPages()
    configureSwagger()

    routing {
        authRoutes()
        usuarioRoutes()
        perfilRoutes()
        specialRoutes()
        exampleRoutes()   // <-- registrado aqui
    }
}
